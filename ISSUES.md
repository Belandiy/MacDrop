# MacDrop — Список задач и технических улучшений (Backlog & Issues)

Документ фиксирует выявленные в ходе реального тестирования нюансы между macOS и Windows, их технические первопричины и детальный план решения.

---

## Issue #1: Не сработало сопряжение по коду устройства (сработало только по IP)

### 📌 Описание проблемы
При попытке связать Mac и Windows через короткий код (например, `MAC-xxxx` или `PC-xxxx`) устройства не находили друг друга. Сопряжение успешно заработало только тогда, когда в приложении был вручную введён прямой локальный IP-адрес одного из компьютеров.

### 🔍 Технический анализ первопричины
1. **Ограничения глобального UDP Broadcast `255.255.255.255`:**
   - В `src/main/discovery.ts` широковещательные пакеты отправляются на адрес `255.255.255.255` (порт 8385).
   - На Windows и macOS при наличии нескольких сетевых интерфейсов (Wi-Fi, Ethernet, виртуальные адаптеры Hyper-V / WSL, VPN, Docker) ОС отправляет broadcast только в интерфейс с наивысшим приоритетом (default route metric). Очень часто этим интерфейсом оказывается виртуальный адаптер WSL или VPN, а не физический Wi-Fi адаптер, через который соединён второй компьютер.
   - Многие роутеры и точки доступа Wi-Fi (особенно при разделении диапазонов 2.4 ГГц и 5 ГГц или включённой изоляции клиентов) намеренно отбрасывают глобальные широковещательные пакеты `255.255.255.255`.
2. **Реактивный поиск в памяти:**
   - Метод `findPeer(code)` ищет только среди тех устройств, от которых за последние 8 секунд уже успел прилететь UDP-пакет. Если пакет был сброшен или заблокирован брандмауэром Windows, устройство считается недоступным, даже если оно находится в той же локальной сети.

### 💡 План решения
1. **Направленный Broadcast по всем физическим интерфейсам:**
   - В `PeerDiscovery.getLocalIps()` перебирать все не-внутренние интерфейсы IPv4.
   - Для каждого интерфейса вычислять его broadcast-адрес подсети (например, при IP `192.168.1.45` и маске `255.255.255.0` отправлять на `192.168.1.255`).
   - Отправлять анонсы на каждый вычисленный broadcast-адрес.
2. **Фоновое экспресс-сканирование подсети (Subnet Probe / Fast Sweep):**
   - Если пользователь ввёл код (например, `MAC-1234`), а устройство ещё не обнаружено по UDP — запускать быстрый параллельный опрос локальной подсети (`192.168.X.1` – `192.168.X.254`) по HTTP на порт 8384 (`/api/ping`).
   - В локальной сети Wi-Fi опрос 254 адресов пачками по 40 потоков с таймаутом 350 мс занимает всего ~1.2 секунды.
   - При ответе сверяется `deviceId`: если код совпал, устройство автоматически добавляется и сопрягается. Это даёт **100% гарантию соединения по коду**, даже если роутер полностью блокирует UDP Broadcast.

## Issue #2: Ложное уведомление «Отправлено» и засорение журнала при выключенном приёме

### 📌 Описание проблемы
Когда на одном компьютере (клиент Б) выключен приём файлов кнопкой **[Выкл]**, второй компьютер (клиент А) при попытке отправки:
1. Сообщает пользователю «Отправлено N файл(ов)!».
2. Копирует файл в свою локальную папку MacDrop.
3. Добавляет неудачную передачу в журнал как ошибку, засоряя историю.

### 🔍 Технический анализ первопричины
1. **Асинхронный вызов в UI:**
   - В `src/renderer/src/components/DropZone.tsx` при броске файлов вызывается `onFilesDropped(paths)`. Но сразу же на следующей строке без ожидания промиса вызывается `setRecentDropSuccess('Отправлено...')`.
2. **Преждевременное локальное копирование:**
   - В `src/main/ipc.ts` в обработчике `send-dropped-files` строка `fs.cpSync(srcPath, destPath)` отрабатывает *до* сетевого запроса `engine.sendItem()`.
3. **Запись в историю при отказе:**
   - В `src/main/engine.ts` при получении HTTP 403 сервер отклоняет файл, но клиент пишет запись в `history` со статусом `failed`.

### 💡 План решения
1. В `DropZone.tsx` и `DeviceDetailView.tsx` дожидаться результата отправки (`await`).
2. Если принимающая сторона вернула HTTP 403 с сообщением `Получатель временно отключил приём файлов`:
   - Показывать пользователю явный статус: **«У второго устройства выключен приём файлов»** (предупреждающий цвет вместо зелёного успеха).
   - **Не добавлять** запись в журнал (`history.push(...)`), чтобы журнал не засорялся при отключенном приёме.
   - **Не копировать** файл в локальную папку, если удалённая отправка отклонена из-за выключенного приёма.

## Issue #3: Папки по умолчанию и расположение macdrop_history.json

### 📌 Описание проблемы
На macOS папка по умолчанию создавалась на рабочем столе (`~/Desktop/MacDrop`), и рядом прямо на рабочем столе появлялся служебный скрытый файл `.macdrop_history.json`.  
Пользователь запросил:
- На Mac: папку по умолчанию сделать `Users/<user>/.macdrop` и там же хранить историю.
- Объяснить, как это работает на Windows, и навести порядок в расположении служебных файлов.

### 🔍 Как это работает сейчас

#### На Windows:
- **Целевая папка (`targetFolder`):**
  1. Код проверяет наличие диска `E:\` (`fs.existsSync('E:\\')`). Если диск существует, создаётся `E:\MacDrop`.
  2. Если диска `E:\` нет (например, только `C:\`), создаётся `C:\Users\<Пользователь>\MacDrop`.
- **Служебный файл истории (`.macdrop_history.json`):**
  - Вычислялся как `path.dirname(config.targetFolder)`.
  - При `E:\MacDrop` файл создавался в корне диска: `E:\.macdrop_history.json`.
  - При `C:\Users\<Пользователь>\MacDrop` файл создавался в домашней папке: `C:\Users\<Пользователь>\.macdrop_history.json`.

#### На macOS:
- Папка по умолчанию задавалась как `~/Desktop/MacDrop`.
- Из-за формулы `path.dirname` скрытый файл истории `.macdrop_history.json` ложился прямо на рабочий стол (`/Users/<user>/Desktop/.macdrop_history.json`), что визуально мешает пользователю.

### 💡 План решения
1. **Для macOS:**
   - Задать папку по умолчанию: `path.join(os.homedir(), '.macdrop')` (`/Users/<user>/.macdrop`).
   - Файл истории сохранять строго внутри этой папки: `/Users/<user>/.macdrop/macdrop_history.json` (или в каталоге данных приложения `app.getPath('userData')`). На рабочий стол ничего не выносить.
2. **Для Windows:**
   - Сохранить приоритет диска `E:\MacDrop` (или `C:\Users\<user>\MacDrop`).
   - Файл истории перенести внутрь самой папки (`targetFolder/.macdrop_history.json`) либо в `app.getPath('userData')/history.json`, чтобы корень диска `E:\` и домашний каталог оставались абсолютно чистыми.
